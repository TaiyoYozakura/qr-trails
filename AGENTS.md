## Local learnings (hard-won, not derivable from the code)

### Next.js 16 / React 19 in this install

- Dynamic route `params` is a **Promise** — every `[id]` page does `const { id } = await params`.
  Bundled reference docs are at `node_modules/next/dist/docs/` (e.g. `01-app/…`); read them
  instead of trusting training data, and heed deprecation notices.
- React here is **19.2.8, which does not export `<ViewTransition>`** (canary-only). Shipped
  page morphs therefore use the native `document.startViewTransition` through
  `src/components/transition-link.tsx` + `src/components/view-name.tsx`.
- The `nextjs-agent-rules` block at the top of this file is **regenerated by `next dev`** —
  append new notes below it rather than editing or deleting it (it will reappear).

### Animation & reduced motion — the bug that keeps coming back

- **Never branch rendered JSX on `useReducedMotion()`.** The server renders with no preference
  and a reduced-motion client renders a different tree, which is a real React hydration
  mismatch. Keep ONE canonical tree, gate only `animate`/`transition` props, and let the root
  `MotionConfig reducedMotion="user"` (`src/components/motion-provider.tsx`, mounted in
  `layout.tsx`) handle the rest. `useReducedMotion()` also returns `boolean | null`.
- Motion's actual reduced-motion semantics (verified in the `motion-dom` dist source): transforms
  jump instantly but **opacity still animates**. So decorative layers must exist unconditionally
  in the canonical tree instead of being conditionally mounted.
- `globals.css` intentionally suppresses the `::view-transition-*(root)` crossfade so the
  shared-element morphs between pages stay clean; route transitions come from `app/template.tsx`.

### Photos / web-sourced images

- Photography lives in **`src/data/images.ts`** (manifest with alt, caption,
  credit, sourceUrl) and the files themselves in **`public/images/`**. Render
  every photo through `components/photo.tsx` so the credit line + source link
  are always output — CC BY / BY-SA require attribution, and the garden photos
  (from the garden's own Google Maps listing, © their photographers) are used
  on a credit + non-commercial basis and should be replaced with the team's own
  shots before any official/commercial use.
- Species photos (neem, mango) are **CC stand-ins, not this garden**; they carry
  `standIn: true`, which the `Photo` component badges as "sample photo".
- Downloading from `upload.wikimedia.org` needs (a) a custom **User-Agent** and
  (b) a thumbnail width from the fixed size buckets (1280 / 1920 / …) — other
  widths return HTTP 400 "Use thumbnail sizes listed on https://w.wiki/GHai".
- Google Maps photos: `lh3.googleusercontent.com/gps-cs-s/…` URLs take a `=sNNN`
  (longest side) or `=wNNN-hNNN` size suffix — append `=s1600-k-no` for a
  high-res still. Drive maps.google.com with the browser tools; the photo grid
  thumbs are CSS backgrounds, so collect them via `getComputedStyle().backgroundImage`.

### Styling — `cn()` does NOT merge Tailwind classes

- `lib/utils.ts`'s `cn()` is a plain string join, **not** tailwind-merge.
  Passing an override via `className` (e.g. `bg-cream text-forest` on a
  `primary` button) does not win by intent — whichever rule comes later in the
  stylesheet wins, so `bg-forest text-cream` can beat it and paint text on the
  same colour (an invisible button that only "fixed itself" on hover).
- When a button needs different colours, **add a variant** to
  `components/button.tsx` (see `onDark` / `outlineDark` for dark-green bands)
  instead of overriding via className.

### Content & data layer

- All garden/flora facts are **placeholder TODOs** (`src/data/garden.ts`, `flora.ts`) waiting on
  real on-site data — never treat them as verified, and don't print or deploy them as fact.
  Partially confirmed from the garden's Google Maps listing (2026-09): hours
  (daily 4–8 pm), 2024 renovation, central Ambedkar statue, play corner with
  slides + small climbing wall; `src/data/play-and-fitness.ts` splits its
  entries by `evidence` ("reported" vs "to-confirm") — keep that honesty when
  adding facilities.
- `src/data/` is the single source of truth: nav, home, explore, the `/qr` sheet and progress all
  derive from it, so adding a trail only touches `trails.ts` + `topics.ts`. Note that the
  discoveries live in **`topics.ts`** (some planning docs call this file `discoveries.ts`).
- The print flow spans three files that must change together: `components/qr-print-page.tsx`
  (client-side `qrcode` rendering) plus the `print:hidden` rules in `header.tsx` / `footer.tsx`.
  Its target list is derived from `trails` + `getTopicsForTrail()` + `plants`, so a printed code
  needs a `Topic.placement` (the physical spot) — that field exists only for the sheet.
- Guidelines live in `data/guidelines.ts` as grouped do/don't items with **string** icon keys
  (`GuidelineIcon`); the Lucide components are mapped in `app/guidelines/page.tsx`, keeping the
  data file free of UI imports.

### Locking / unlocking — three files that must agree

- `?scan=1` is the **only** unlock trigger. `/learn/[id]` and `/quiz/[id]` read it
  from `searchParams` (Next 16: a Promise) and pass it to `components/unlock-gate.tsx`,
  which records it in `localStorage` via `unlockTopic()`. Nothing else may unlock a
  stop, and no internal link should point at a locked stop.
- Because those pages read `searchParams`, they are **server-rendered on demand**
  (build output shows `ƒ`) and can no longer be statically exported. `generateStaticParams`
  was removed from both — it is silently ignored on a dynamic route.
- **Locked-page precision:** the *rendered HTML* shows only the scan prompt, but
  the embedded RSC flight payload (visible via view-source) still serialises the
  content tree — the client gate needs it to reveal the page after hydration.
  So "content never sent" is true for what a visitor *sees*, not for what a
  determined view-source reader can extract. Closing that would mean splitting
  the page server-side (content only when `?scan=1` was in the URL) at the cost
  of the localStorage-reveal for returning visitors.
- The `/qr` sheet must keep generating `/learn/<id>?scan=1` (`components/qr-print-page.tsx`);
  a code without the query produces a permanently locked stop in the garden.
- Lock-aware UI: `topic-step-link.tsx` (prev/next + result CTA) and `trail-path.tsx`
  (disabled nodes). Use them instead of hand-writing `/learn/x` links, or a visitor
  will be sent straight into the locked screen.
- `useProgress()` reads through `useSyncExternalStore` with an **empty server
  snapshot**, so server and first client render always agree on "locked". Do not
  switch it back to reading localStorage during render — that desyncs hydration.
  Completed stops also count as unlocked (pre-locking progress keeps working).

### Admin console — a separate view, with a draft that is not a CMS

- **Two views, not one app with sections.** `components/header.tsx` and
  `footer.tsx` both `return null` when `usePathname()` starts with `/admin`;
  `/admin/*` gets its own chrome from `app/admin/layout.tsx` (which also sets
  `robots: noindex`). The printable QR sheet now lives at `/admin/qr` — the old
  public `/qr` route was deleted, so do not re-add links to it.
- **The passcode gate is decoration, not security** (`lib/admin.ts`): the site is
  static, so `NEXT_PUBLIC_ADMIN_PASSCODE` ships inside the client bundle. Read the
  comment there before believing otherwise, and never put anything truly private
  in this repo.
- **Visitors never read the draft.** The console edits `localStorage`
  (`qr-trails:content-draft`, `lib/draft-store.ts`) and can only *export* — the
  site keeps reading `src/data/*`. So an admin edit changes nothing for visitors
  until it is pasted into `src/data` and rebuilt; that is deliberate, and the
  shell shows a permanent "draft saved in this browser only" banner so nobody is
  misled. A real CMS would need a backend.
- **Export is codegen, not a format of its own**: `lib/content-tools.ts` turns the
  draft back into TypeScript for the four data files. If you change a type in
  `types.ts`, check the generators still produce compiling output.
- **Id edits must go through `renameTrailId` / `renameTopicId` / `renameQuizId`**
  (same file) — they rewrite the cross-references (trail stop order, `topicId`,
  `quizId`). Hand-editing an id leaves orphaned references that only the console's
  own Checks panel will notice.
- **Option lists live in `types.ts`** (`VISUAL_KINDS`, `GUIDELINE_ICONS`) so the
  admin pickers and the illustration/icon maps share one source; both maps are
  typed exhaustively, so a new entry fails to compile until it is wired up.

### Architecture constraint to preserve

The spec requires a **fully static, backend-free** site (no DB, accounts, or analytics) and this
build prerenders every route. Proposals for admin sign-in, middleware or signed QR tokens would
break that and need explicit user sign-off first.
